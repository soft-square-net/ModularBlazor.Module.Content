# ModularBlazor.Module.Content

Content: newsroom posts (article, news, video, reportage and other post kinds), taxonomy, and the review and publishing workflow. It is a module of the [ModularBlazor](https://github.com/soft-square-net/ModularBlazor.Platform) platform, released on its own as the bundle `content`.

> **Status: moved in.** The code moved here from the platform repo and builds against the platform packages.
> Nothing here is packed as a bundle yet: build it and upload the entry project's output in the admin area.

A post is a document composed of **shared contents** that sections work on and the Desk reviews, through a pipeline
stored as data; see [docs/shared-contents.md](docs/shared-contents.md).

## Layout

The server part follows [Ardalis Clean Architecture](https://github.com/ardalis/CleanArchitecture), adapted to a
runtime module: see [docs/clean-architecture.md](docs/clean-architecture.md) for the layers, the dependency rules and
where a new feature goes.

```
src/WebApi.Modules.Content.Core/             Core: aggregates (PostAggregate, PressAggregate, CategoryAggregate), domain rules, specifications
src/WebApi.Modules.Content.UseCases/         use cases: one folder each, a Mediator command or query and its handler, returning an Ardalis Result
src/WebApi.Modules.Content.Infrastructure/   data: ContentDbContext, entity configurations, tenant migrations per database provider
src/WebApi.Modules.Content.Web/              entry assembly: IRuntimeModule, the Carter route table, one REPR endpoint class per route
src/WebApi.Modules.Content.Client/           typed API client (NSwag), shipped as a hidden client module
src/Module.Content/                          Blazor client module "Contents Management": posts, workflow, presses and categories
src/openapi/   the saved OpenAPI document the client is generated from
tests/         UnitTests (Core, UseCases; NSubstitute) and IntegrationTests (Infrastructure on SQLite)
playground/    Aspire AppHost: the platform (from a Platform checkout) with this module, see "Developing"
docs/          clean-architecture.md
module.json    bundle manifest, generated by the pack step
```

## Building

```bash
dotnet build
dotnet test
```

The platform packages come from the soft-square-net GitHub Packages feed, which needs a token to restore even though
the packages are public: create a personal access token (classic) with `read:packages` and put it in the environment
as `GITHUB_PACKAGES_TOKEN` (`NuGet.Config` reads it). The platform version is pinned once, in `global.json`.

Tools that need the platform's source run from a checkout of
[ModularBlazor.Platform](https://github.com/soft-square-net/ModularBlazor.Platform), pointed at this repo. Re-export the
OpenAPI document (the entry project is `Web`):

```powershell
./src/WebApi/scripts/Export-ModuleOpenApi.ps1 -Project <this repo>/src/WebApi.Modules.Content.Web -ModuleId content
```

Add a migration for every database provider (the migrations live in `Infrastructure/Data/Migrations/<Provider>`, so
the folder and namespace are passed):

```powershell
./src/WebApi/scripts/Add-Migration.ps1 -Project <this repo>/src/WebApi.Modules.Content.Infrastructure -Name <Name> `
    -MigrationsDir Data/Migrations -Namespace soft.square.net.WebApi.Modules.Content.Infrastructure.Data.Migrations
```

## How it builds and ships

- It compiles against the platform's contract packages (`WebApi.Contracts`, `ModularBlazor.Abstractions`, ...) from the
  soft-square-net GitHub Packages feed. It never references platform source.
- CI packs one bundle per release: `<module>-<version>.modpkg`, a zip with `module.json`, `server/`, `client/` and
  `contracts/`. The platform's admin area installs it: server part first (tenant migrations), then the client part.
- One version for the whole bundle, set once from the git tag. Unchanged parts are skipped on install.
- An API client ships once, inside the bundle that owns the API, as a hidden client module. Modules that call it
  reference its package with `ExcludeAssets="runtime"` and declare a dependency with a version range in `module.json`.

This repo's bundle has three parts:

| Part | Project | Installed on |
| --- | --- | --- |
| server | `WebApi.Modules.Content.Web` (its build output, zipped: every server layer plus the private Mediator and Ardalis.Result) | Host Modules (`/host-modules`) |
| client, hidden | `WebApi.Modules.Content.Client` (`WebApi.Modules.Content.Client`) | Client Modules (`/client-modules`) |
| client | `Module.Content` (`Module.Content`): menu item "Contents Management", pages under `/contents` | Client Modules, after the API client |

`Module.Content` lists the API client in its `Dependencies` and references it with `Private="false"`, so its output
holds only `soft.square.net.Module.Content.dll`. Until the pack step exists the parts are uploaded one by one, in the
order above. The pages call the tenant-bound Content API: sign in to a tenant (the client's sign-in page asks for the
organisation) and hold the `content.*` permissions for what you do there.

## Developing

`playground/` is a small Aspire AppHost: PostgreSQL, the identity service, one WebApi and the Blazor client, with this
module in it. It builds the platform from source, from a
[ModularBlazor.Platform](https://github.com/soft-square-net/ModularBlazor.Platform) checkout next to this repo:

```
<workspace>/Platform          git clone https://github.com/soft-square-net/ModularBlazor.Platform Platform
<workspace>/Module.Content    this repo
```

(another location: `-p:PlatformRoot=<path>/`). It uses the platform lab's ports (identity 5090, API 5080, client
5070), so stop the Hybird lab first. It has two launch profiles:

| Profile | What it does | Use it for |
| --- | --- | --- |
| `dev` (default) | The WebApi loads the module straight from `src/WebApi.Modules.Content.Web/bin/<Configuration>/net10.0` (`Modules:Local`, Development only): installed and active on start, and the client parts with it | Daily work: change code, rebuild, restart the `webapi` resource in the dashboard (or F5 again), reload the browser |
| `install` | The platform starts without the module, as in production; every build zips the module to `playground/out/content.zip` | Before a release: upload the zip on http://localhost:5070/host-modules (sign in as the dev platform admin, `admin@modular.local`) and activate it, which runs the real install path |

The client parts load in the browser from the client-modules catalog. The playground keeps that catalog in
`playground/.data`, not in the platform checkout, through the WebApi's host override
`Modules:Settings:client-modules:ClientModules:Path`.

- **`dev` profile:** every start installs both client parts from their build output, the API client first. This is
  the client-modules module's `ClientModules:Local`, Development only, also set through a host override. The menu item
  "Contents Management" is there without an upload.
- **`install` profile:** upload them yourself on http://localhost:5070/client-modules:
  `soft.square.net.WebApi.Modules.Content.Client.dll` first, then `soft.square.net.Module.Content.dll`. Both are in
  `playground/out/client/`. The catalog refuses the UI until the API client is installed.

To use the pages, sign out, then sign in with the organisation `acme` as one of its dev accounts. The passwords are
in the platform's `WebApi.Identity.Server/appsettings.Development.json`.

| Account | Content permissions in `acme` (given by the playground) |
| --- | --- |
| `acme-admin@modular.local` | All of them (`content.*`): taxonomy, writing, the review steps, publishing |
| `editor@modular.local` | `content.author`: writes posts and submits them for review |

The platform admin (`admin@modular.local`) has no tenant, so the pages show "400: no tenant" for it.

```bash
dotnet run --project playground --launch-profile dev
```

```bash
dotnet run --project playground --launch-profile install
```

In Development the platform seeds the dev tenants `acme` and `globex` on the playground's server, so tenant APIs work
right away: call them with the header `X-Tenant: acme`. Writing content needs the module's permissions in that tenant.
The playground gives them to the dev accounts above through the WebApi's `Access:DevGrants` (Development only, by
email). The first time each account calls the API in `acme`, it gets them as ordinary grants with the source `dev`.
Data stays in the Docker volume
`content-playground-data` and in `playground/.data` (the host and client module catalogs); delete both to start over.

The playground is not in `ModularBlazor.Module.Content.slnx`: CI builds the module without a platform checkout.

To translate posts in the playground, load the DynamicFields module beside Content: build a
[Module.DynamicFields](https://github.com/soft-square-net/ModularBlazor.Module.DynamicFields) checkout next to this repo
(or pass `--Playground:DynamicFields=<path>`), then install its starter fields on its Fields page.

```bash
dotnet run --project playground -- --Playground:DynamicFields=../Module.DynamicFields
```

## Translations

A post's document is written in one language. Each other language is a **translation overlay** kept with the post:
per node id (`$root` for the document's root) and content key, the translated text and the hash of the source it was
translated from. DynamicFields owns the format and its rules; Contents stores and serves it.

| Endpoint | What it does |
| --- | --- |
| `PUT /posts/{id}/translations/{language}` `{ version, nodes }` | Adds or replaces one language. Whoever may edit the post now may translate it (owner in their window, the assigned reviewer on shift, Desk). The workflow state does not change |
| `DELETE /posts/{id}/translations/{language}?version=` | Removes one language |
| `GET /public/{publicId}?culture=ar-EG` | The published document with its text from the `ar-EG` translation, then `ar`, then its own; `languages` lists what it is translated into, `servedLanguages` what this answer used |

- **Checks:** Contents checks what it can without the field definitions: a language tag, nodes the document has, keys
  whose source is text, the same shape (text or list of texts), a source hash, 2 MB at most, 20 languages at most.
  The schema rules (which properties are translatable, their lengths) are DynamicFields' and are checked by its
  translate dialog before it returns. Modules load in isolated contexts, so Contents does not call it on the server.
- **Edits:** editing the document drops the translated values of nodes and keys it no longer has. A changed source
  value keeps its translation; the dialog shows it as stale.
- **Publishing:** the translations are published with the document. On a published post whose live version is the
  current one, a translation change is live at once; otherwise it goes live with the next publication.
- **UI:** the post page lists the translations and opens `Module.DynamicFields/translate-content` to add or edit one,
  when that dialog is installed.
