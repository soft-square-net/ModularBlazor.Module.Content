# ModularBlazor.Module.Content

[العربية](README.ar.md)

Content: newsroom posts (article, news, video, reportage and other post kinds), taxonomy, and the review and publishing workflow. It is a module of the [ModularBlazor](https://github.com/soft-square-net/ModularBlazor.Platform) platform, released on its own as the bundle `content`.

> **Status: moved in.** The code moved here from the platform repo and builds against the platform packages.
> Nothing here is packed as a bundle yet: build it and upload the entry project's output in the admin area.

A post is a document composed of **shared contents** that sections work on and the Desk reviews, through a pipeline
stored as data; see [docs/shared-contents.md](docs/shared-contents.md).

## Layout

The server part follows [Ardalis Clean Architecture](https://github.com/ardalis/CleanArchitecture), adapted to a
runtime module: see [docs/clean-architecture.md](docs/clean-architecture.md) for the layers, the dependency rules and
where a new feature goes.

```
src/Content.Contracts/                       the package soft.square.net.Content.Contracts: content.* event records, ContentWorkItems, ContentLiveTopic
src/WebApi.Modules.Content.Core/             Core: aggregates (PostAggregate, PressAggregate, CategoryAggregate), domain rules, specifications
src/WebApi.Modules.Content.UseCases/         use cases: one folder each, a Mediator command or query and its handler, returning an Ardalis Result
src/WebApi.Modules.Content.Infrastructure/   data: ContentDbContext, entity configurations, tenant migrations per database provider
src/WebApi.Modules.Content.Web/              entry assembly: IRuntimeModule, the Carter route table, one REPR endpoint class per route
src/WebApi.Modules.Content.Client/           typed API client (NSwag), shipped as a hidden client module
src/Module.Content/                          Blazor client module "Contents Management": posts, workflow, presses and categories
src/openapi/   the saved OpenAPI document the client is generated from
tests/         UnitTests (Core, UseCases, Web declarations; NSubstitute), IntegrationTests (Infrastructure on SQLite) and
               MigrationTests (every migration on PostgreSQL, SQL Server, MySQL and Oracle in Docker)
playground/    Aspire AppHost: the platform (from a Platform checkout) with this module, see "Developing"
docs/          clean-architecture.md
module.json    bundle manifest, generated by the pack step
```

## How it builds and ships

- It compiles against the platform's contract packages (`WebApi.Contracts`, `ModularBlazor.Abstractions`, ...) from the
  soft-square-net GitHub Packages feed. It never references platform source.
- CI packs one bundle per release: `<module>-<version>.modpkg`, a zip with `module.json`, `server/`, `client/` and
  `contracts/`. The platform's admin area installs it: server part first (tenant migrations), then the client part.
- One version for the whole bundle, set once from the git tag. Unchanged parts are skipped on install.
- An API client ships once, inside the bundle that owns the API, as a hidden client module. Modules that call it
  reference its package with `ExcludeAssets="runtime"` and declare a dependency with a version range in `module.json`.

This repo's bundle has three parts:

| Part | Project | Installed on |
| --- | --- | --- |
| server | `WebApi.Modules.Content.Web` (its build output, zipped: every server layer plus the private Mediator and Ardalis.Result) | Host Modules (`/host-modules`) |
| client, hidden | `WebApi.Modules.Content.Client` (`WebApi.Modules.Content.Client`) | Client Modules (`/client-modules`) |
| client | `Module.Content` (`Module.Content`): menu item "Contents Management", pages under `/contents` | Client Modules, after the API client |

`Module.Content` lists the API client in its `Dependencies` and references it with `Private="false"`, so its output
holds only `soft.square.net.Module.Content.dll`. Until the pack step exists the parts are uploaded one by one, in the
order above. The pages call the tenant-bound Content API: sign in to a tenant (the client's sign-in page asks for the
organisation) and hold the `content.*` permissions for what you do there.

## Post kinds and URLs

A post's kind (`postKind`) is the key of a **DynamicFields root post field**: `post.article`, `post.news`, or any root
field the tenant publishes. Its static URL prefix comes from that field.

- **Reading the kinds.** Content reads them through the gateway (`Content:ApiBaseUrl`) from DynamicFields'
  `GET /api/dynamicfields/catalog/root-post-fields`, with the caller's token and tenant. The list is cached per tenant
  for `Content:PostKindCacheSeconds` (default 60). A failure isn't cached.
- **Creating a post.** Its kind must be in that list. Otherwise the answer is 400; if DynamicFields can't be reached, it's 503.
- **The picker.** `GET /kinds` returns that list (`key`, `title`, `urlPrefix`, `schemaType`, `version`), or 503. The
  new-post form offers it. It translates the starter library's titles and shows any other title as the tenant wrote it.
  While the list can't be read, the form says so and offers the eight starter kinds.
- **The new post's root.** Without a `document`, the post's root is its kind's field at its published `version`, with
  the title as `headline` when the field has that value (read from `GET /api/dynamicfields/fields/{key}/versions/{n}`).
  A later title change moves the headline with it while the two are still equal. The kind's other required values
  (summary, image, ...) are still required: approve, schedule and publish refuse the post (422) until they're filled in.
- **Setting the values.** `PUT /posts/{id}/root { version, fieldVersion, content, style? }` replaces the root's values
  and style (whoever may edit the post now). The contents, title and body stay. The post page does this with
  DynamicFields' `edit-content` dialog.
- **Posts made before this** have the root `legacy.basic` (title and body), which is no DynamicFields field, so the
  designer's check fails on them. Nothing converts them silently, and there's no migration (the field versions are each
  tenant's). The post page marks such a post, and **Fill in the values** (the same `PUT .../root`) gives it its kind's
  root. The title, body, contents and published snapshot stay, and a translated `title` becomes the translated
  `headline`. The upgrade is refused if anything would be lost: another value in the old root, or a translated `body`.
- **Publishing (decision D3).** A post whose kind has no published root field can still be edited. Publishing or
  scheduling it is refused with 409: "... has no published DynamicFields root post field, so it has no URL and cannot
  be published yet". A due scheduled post in that state stays scheduled, and a later run publishes it.
- **URLs.** When a post is published, its kind's prefix is kept with the live version (`PublishedUrlPrefix`). Its
  canonical path is `/{urlPrefix}/{slug}`. The slug is the one of the served culture, else of its first culture, else the
  public id.
  - `GET /posts/{id}` returns `urlPrefix` (the kind's prefix now, null while it has none) and `canonicalPath` (the
    live version's path).
  - `GET /public/{publicId}` returns both without calling DynamicFields, so anonymous readers get them too. It also
    returns the published `body`: a kind's root has no value for it.
  - Posts published before this release have no prefix until they're published again.
- **Old kinds.** Until wave 4 the kind was an enum. The `PostKindsAsFieldKeys` migration maps its names to keys, in the
  kind columns and in the stored documents and contents:

  | Old name | Key |
  | --- | --- |
  | `Article` | `post.article` |
  | `News` | `post.news` |
  | `Video` | `post.video` |
  | `Reportage` | `post.reportage` |
  | `PhotoStory` | `post.photo-story` |
  | `Other` | `post.other` |

  For one release the API still accepts the old names (and their numbers) as input. It always returns keys.
  DynamicFields' starter library has root fields for the first two; the others come with its starter kinds.

## Categories and units

**Categories.** A post is in one **primary** category and any number of others (at most 20), **all of its press**
(decision D4).

- `PostDetail.categoryId` is the primary one; `categories` lists them all, the primary first. `PostSummary.categoryId`
  is the primary one.
- `POST /posts` takes `categoryIds` (more categories) next to `categoryId`; the author right is needed in each.
- `PUT /posts/{id}/categories { version, primaryCategoryId, categoryIds }` changes them. Who may: the post's editors (its
  owner while it is editable, its reviewer on shift, the Desk) or the workflow (`content.unit.assign`). A category the
  post is not in yet also needs the author right or a seeing right in it. A category of another press is 400.
- A category change is a new version, but an approval or a schedule stays valid: the document did not change.
- Each category has `nameEn` and `nameAr` (`name` is the English one, for older clients). `POST /categories` takes
  `nameEn` and `nameAr`, or `name`; without an Arabic name it takes the English one.
- Storage: the primary category keeps its column (`articles.CategoryId`); every category, the primary one too, is a row
  of `post_categories`, always loaded with the post. The `UnitsAndCategories` migration makes each post's category its
  first row, and starts every Arabic name as the English one.

**Units.** A post (`unitId`, `unitPath`) and a content (`unitId`, `unitPath`) can belong to an **Organization unit**.

- **Only the workflow sets it:** `PUT /posts/{id}/unit` and `PUT /contents/{id}/unit` `{ version, unitId? }` need
  `content.unit.assign`, a permission meant for the workflow's service client and granted to nobody else by default.
  Ordinary callers get 403. The moderator's choice reaches Content through the workflow. Pages show the unit read-only.
- **The unit must serve the post:** its categories (Organization's `CategoriesOf`) must include one of the post's
  categories (the content's category). `*` serves every category (D1). Otherwise 409; an unknown unit is 400; when
  Organization can't be reached, 503.
- **Reading units.** Content reads a unit through the gateway (`Content:ApiBaseUrl`) from Organization's local directory
  (`GET /api/organization/local/units/{id}` and `.../categories`, with `HttpUnitDirectory`), with the caller's token and
  tenant. It's cached per tenant for `Content:UnitCacheSeconds` (default 60), and dropped on any `org.unit-*.v1` event.
- **Paths.** The unit's path (`/{root}/.../{unit}`, N-form ids) is stored with the post and the content, so rights checks
  and the live hub need no call to Organization. `org.unit-moved.v1` rebases the stored paths at and below the unit.
- **Scopes.** A post's scopes are `press:{p}`, `category:{c}` for every category, and `unit:{id}` for its unit and each
  ancestor (`UnitScopes.For(path)`). A content's are its `press:` and `category:`, its unit's `unit:` scopes and
  `section:{unit id, N form}` (the department rota's grant), or, before its section moved, `section:{section id}`. A unit
  grant covers everything below the unit, in checks and in the post and content lists.
- **Shifts sections.** `ContentItem.SectionId` held Shifts section ids. `shifts.section-moved.v1 { sectionId, unitId }`
  (with the unit's path in the envelope) remaps every content of that section to the unit and clears the section. The
  column stays until Shifts removes sections (S4).

Content subscribes to `shifts.section-moved.v1` and `org.unit-*.v1` (the manifest's `Subscriptions`). The events it
publishes are listed under "Work items, checks and events".

## Who assigns work

Moving work between people is five steps: a post's **accept**, **assign**, **transfer** and **return**, and a content's
**assign** (`POST /contents/{id}/assign`). The setting `Content:Newsroom:WorkflowOwnsAssignment` (default **false**) says
who may take them.

| Step | `false` (default): the manual desk | `true`: the workflow only |
| --- | --- | --- |
| `POST /posts/{id}/accept` | `content.accept` in the named active shift | `content.unit.assign` |
| `POST /posts/{id}/assign` | `content.assign` in the named active shift | `content.unit.assign` |
| `POST /posts/{id}/transfer` | `content.transfer` | `content.unit.assign` |
| `POST /posts/{id}/return` | `content.return` (shift Manager, Desk) | `content.unit.assign` |
| `POST /contents/{id}/assign` | `content.assign` | `content.unit.assign` |

- Every right is checked on the post's or the content's scopes (see "Categories and units").
- With `true`, `content.unit.assign` **replaces** the right of the left column: ordinary users get 403, the shift manager
  and the Desk too, and the workflow's service client needs no shift.
- The other rules don't change. Accept still records a shift id, assign still names a shift on which the assignee holds
  `content.review` for the post (otherwise 409), and each step still needs the post in a state it can start from.
- Keep it `false` until the NewsRoom workflow runs: with `true` and no workflow, nobody can assign work. The pages
  still show the buttons; the API decides.
- It does not change these:
  - `POST /automation/auto-assign/{id}` still needs `content.assign` and then takes the assign step, so with `true` its
    caller needs `content.unit.assign` too.
  - `POST /automation/handover` keeps its own rule, tenant-wide `content.transfer`.
  - `POST /contents` may still name a first assignee, with the author right.

## Work items, checks and events

**A content is a work item; its stage is the state.** Each content of the library is the platform work item
`content:content:{contentId}` (`ContentWorkItems` in `Content.Contracts`).

- The built-in pipeline's stages are the agreed states: `assigned` → `in-progress` → `submitted` → `in-review` →
  `accepted` | `returned`.

  | Stage | Kind | Who edits | Actions from it |
  | --- | --- | --- | --- |
  | `assigned` (start) | Work | assignee | `start` → in-progress, `submit` → submitted; the first edit moves it to `in-progress` |
  | `in-progress` | Work | assignee | `submit` |
  | `submitted` | Review | `content.publish` | `review` → in-review, `accept` → accepted, `return` (note) → returned |
  | `in-review` | Review | `content.publish` | `accept`, `return` |
  | `accepted` | Accepted | `content.publish` (an edit sends it back to `in-review`) | `return`, `reopen` → in-review |
  | `returned` | Work | assignee | `start`, `submit`; the first edit moves it to `in-progress` |

- **Old keys.** The first pipeline's keys were `draft`, `desk`, `accepted`, `rejected` and the action `reject`.

  | Old | New |
  | --- | --- |
  | `draft` | `assigned` |
  | `desk` | `submitted` |
  | `rejected` | `returned` |
  | `accepted` | `accepted` (unchanged) |
  | action `reject` | action `return` (`POST /contents/{id}/act` still takes `reject`) |

  The migration `WorkItemStages` renames the stored stages and a published pipeline's keys on every engine. Elsa may
  still publish the old keys: `PUT /pipeline` renames them the same way, unless the definition already has a stage with
  the new key. History rows and old feed rows keep the keys they were written with.
- **Events.** Every stage move publishes `content.work-item-state-changed.v1`, and every assignment
  `content.work-item-assigned.v1` (the platform's `WorkItemStateChanged` / `WorkItemAssigned`), in the same save.
  The snapshot is `ref content:content:{id}`, `title` (the content's first text value), `state` (the stage key),
  `assignee` (`{kind:"user", id}` or null), `dueAt` (null) and `unitId` (N form). The subject is the reference, and the
  envelope carries the content's unit path.

**DynamicFields checks first.**

- Any content action into a `Review` or `Accepted` stage first runs DynamicFields `validate-node` on the content and on
  each nested node.
- A post's approve, schedule and publish first run `validate` on the whole post (its working document). A legacy
  title-and-body root has its contents checked one by one.
- Problems: **422**, problem details with `problems: [{ path, message, nodeId }]`. Nothing changes, but the refusal is
  recorded: the feed row `content.validation-failed` and the event `content.validation-failed.v1`.
- DynamicFields can't be reached, or refuses the call: **503**, and the step waits (it never passes unchecked).
- The calls go through the gateway (`Content:ApiBaseUrl`) with the caller's token and tenant, so the caller needs
  `dynamicfields.read`. An unpublished field version (`validate-node` answers 404) is a problem at `/field`.

**Integration events** (source `content`; records in `Content.Contracts`, `ContentEventTypes`). All are written to the
outbox in the save that makes the change, and sent once it commits.

| Event | When | Subject | Data |
| --- | --- | --- | --- |
| `content.post-created.v1` | a post is created (with the post's save, in one transaction) | `post:{id}` | `PostCreated`: `postId, publicId, version, postKind, title, ownerId, state, pressId, primaryCategoryId, categories, contents, unitId, unitPath, createdAt` |
| `content.post-categories-changed.v1` | a post's categories changed | `post:{id}` | `postId, publicId, version, pressId, primaryCategoryId, categories, previousCategories, unitId, unitPath` |
| `content.post-unit-changed.v1` | a post's unit changed | `post:{id}` | `postId, publicId, version, pressId, primaryCategoryId, categories, unitId, unitPath, previousUnitId` |
| `content.validation-failed.v1` | DynamicFields refused a step | `post:{id}` or `content:{id}` | `ContentValidationFailed`: `check (node/post), action, contentId, postId, version, problems, by, at` |
| `content.work-item-assigned.v1` | a content got an assignee | `content:content:{id}` | the platform's `WorkItemAssigned` |
| `content.work-item-state-changed.v1` | a content moved to another stage | `content:content:{id}` | the platform's `WorkItemStateChanged` |
| one per feed type, below | every feed row (`GET /events`) | `post:{id}`, else `content:{id}` | `ContentFeedEvent`: `feedType, postId, contentId, version, revision, stage, postState, by, at, detail` |

The feed rows, mapped one to one (`ContentEventTypes.OfFeedType`):

| Feed type | Event |
| --- | --- |
| `content.created` | `content.content-created.v1` |
| `content.changed` | `content.content-changed.v1` |
| `content.state-changed` | `content.content-state-changed.v1` |
| `content.assigned` | `content.content-assigned.v1` |
| `content.archived` | `content.content-archived.v1` |
| `content.deleted` | `content.content-deleted.v1` |
| `content.attached` | `content.content-attached.v1` |
| `content.detached` | `content.content-detached.v1` |
| `post.changed` | `content.post-changed.v1` |
| `post.state-changed` | `content.post-state-changed.v1` |

**The package `soft.square.net.Content.Contracts`** (`src/Content.Contracts`, BCL only, so any module can copy it

## Migrations

There is one migration set per engine (`Infrastructure/Data/Migrations/<Provider>`). `tests/WebApi.Modules.Content.MigrationTests`
runs every set against a real database in Docker (Testcontainers): PostgreSQL 17, SQL Server 2022, MySQL 8.4 and
Oracle Free 23. For each engine it:

- applies every migration to an empty database;
- checks the data step of `PostKindsAsFieldKeys` both ways;
- checks `UnitsAndCategories`: posts keep their categories and unit, and down and up again a post's category becomes its
  `post_categories` row and the Arabic names start as the English ones; the integration outbox and inbox exist;
- checks `WorkItemStages`: down, a content in `in-progress` goes back to `draft`; up, the old keys become the work-item
  states, in the contents and in a pipeline published with the old keys (its definition is read back through EF);
- runs every Down and every Up again;
- checks that the model snapshot matches the model (`HasPendingModelChanges`; this check needs no Docker).

Without Docker the database tests are skipped. Run it alone with:

```bash
dotnet test tests/WebApi.Modules.Content.MigrationTests
```

## Lookups and live updates

**Lookup `content.categories`** (`Web/Lookups/ContentLookups.cs`, served by the host from the tenant's database):

| Request | Answer |
| --- | --- |
| `GET /api/content/lookups/categories?q=&skip=&take=` | `{ items: [{ key, text }], hasMore }`: the tenant's categories, key = category id, text = the English name (the Arabic one in `ar`), ordered by the English name |
| `GET /api/content/lookups/categories?parent={pressId}` | the categories of one press |
| `GET /api/content/lookups/categories/keys?keys=ahram-sports,daily-politics` | the text of saved ids |
| `POST /api/content/lookups/categories/query` | the picker: filter on `PressId`; the `PressId`, `NameEn` and `NameAr` columns in `extra` |

- Search runs on both names and the id.
- Paging follows the platform contract: `take` is at most 100, and `hasMore` is read from take + 1 rows.
- Like `GET /categories`, it needs a signed-in user and no permission.

**Live topic `content:post:{id}`** (`UseCases/Live/PostLive.cs`):

- **Manifest:** one declaration, `LiveTopic.AnyOf("post", content.author + PostAccess.SeeingPermissions)`. Any one of
  these is enough: `content.author`, `content.accept`, `content.assign`, `content.return`, `content.publish`,
  `content.editor`, `content.manage`, `content.unit.assign`.
  - Content has no single "read a post" permission, so the topic lists the authors' (the studio's users) and every one
    that shows other people's posts. So the shift manager and the Desk get live updates without the author right.
  - `content.review` is not in the list: a reviewer who holds none of these polls.
  - The platform refuses a manifest that declares a kind twice.
  - The hub checks them on `post:{id}`, and on the post's `press:`, `category:` (every category) and `unit:` (its unit and the unit's ancestors) scopes from `PostLiveScopeResolver` (an `ILiveScopeResolver` in the module's services).
  - The resolver runs only where Content is loaded on the hub's pool (core).
  - A caller without the right is refused, and the ContentDesigner studio then polls the feed.
- **Messages:** once the feed rows (`FeedEntry`) of a save are committed, `LivePostPublisher` publishes `post.changed` with `{ eventId, type, contentId? }` and `sequence: null`.
  - The message goes to the row's post.
  - A content's row (no post id) goes to every post that uses that content.
  - Clients re-read `GET /posts/{id}/events?after=`.
  - The sequence is null because feed ids are global per tenant: they would look like gaps on a post's topic.
- **When:** `ContentDbContext` publishes after the save, or, inside an explicit transaction, when it commits. A rollback sends nothing.
- **Failures:** a failed publish is logged and never fails the save. Without a live notifier (an older host) nothing is sent.

## Translations

A post's document is written in one language. Each other language is a **translation overlay** kept with the post:
per node id (`$root` for the document's root) and content key, the translated text and the hash of the source it was
translated from. DynamicFields owns the format and its rules; Contents stores and serves it.

| Endpoint | What it does |
| --- | --- |
| `PUT /posts/{id}/translations/{language}` `{ version, nodes }` | Adds or replaces one language. Whoever may edit the post now may translate it (owner in their window, the assigned reviewer on shift, Desk). The workflow state does not change |
| `DELETE /posts/{id}/translations/{language}?version=` | Removes one language |
| `GET /public/{publicId}?culture=ar-EG` | The published document with its text from the `ar-EG` translation, then `ar`, then its own; `languages` lists what it is translated into, `servedLanguages` what this answer used |

- **Checks:** Contents checks what it can without the field definitions: a language tag, nodes the document has, keys
  whose source is text, the same shape (text or list of texts), a source hash, 2 MB at most, 20 languages at most.
  The schema rules (which properties are translatable, their lengths) are DynamicFields' and are checked by its
  translate dialog before it returns. Modules load in isolated contexts, so Contents does not call it on the server.
- **Edits:** editing the document drops the translated values of nodes and keys it no longer has. A changed source
  value keeps its translation; the dialog shows it as stale.
- **Publishing:** the translations are published with the document. On a published post whose live version is the
  current one, a translation change is live at once; otherwise it goes live with the next publication.
- **UI:** the post page lists the translations and opens `Module.DynamicFields/translate-content` to add or edit one,
  when that dialog is installed.
